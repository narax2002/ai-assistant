# Project Roadmap

## 문서 범위
이 문서는 멀티에이전트 리서치 비서 프로젝트의 제품 로드맵이다.
세션별 상태는 `markdown/current-status.md`를 참고하고, Python/C 역할 분리 전략은 `markdown/c-core-python-api-roadmap.md`에서 별도로 다룬다.

## 진행 상황 요약
- Phase 0~3 완료 (2026-04-07 기준)
- 그린필드 구조로 재시작하여 멀티에이전트 파이프라인 구축 완료
- DuckDuckGo 웹 검색 연동, 실제 출처 URL 제공
- 모델: gemma3:4b (Ollama), Discord 슬래시 커맨드

## 1차 제품 목표
이 프로젝트의 1차 목표는 다음 한 문장으로 정리한다.

> Discord에서 동작하는 개인용 멀티에이전트 리서치 비서 MVP를 만들어, AI/개발 관련 질문에 대해 자료 수집, 비교, 요약, 다음 행동 제안까지 자동으로 제공한다.

초기에는 범위를 넓히지 않고 아래 주제에 집중한다.

- 로컬 LLM
- Ollama
- RAG
- 멀티에이전트 설계
- AI 자동화 도구 비교
- 개발 워크플로와 코딩 에이전트 관련 조사

## 이 방향을 선택하는 이유
- 캘린더나 메일 자동화보다 안전하다. 초기에는 읽기와 정리에 집중하므로 외부 시스템에 잘못 쓰는 리스크가 낮다.
- 멀티에이전트 구조의 장점이 잘 드러난다. 조사, 비교, 요약 역할을 분리하면 품질 차이를 측정하기 쉽다.
- 개인 생산성 체감이 크다. 단순 일정 조회보다 복잡한 기술 주제 정리가 더 자주 쓰일 가능성이 높다.
- 이후 확장이 쉽다. 리서치 비서가 안정화되면 Notion 저장, TODO 생성, 학습 계획 생성, 캘린더 연동으로 자연스럽게 확장할 수 있다.

## 초기 제품 범위
초기 MVP는 아래 기능만 확실히 한다.

- Discord에서 질문을 받는다.
- 질문을 작업 단위로 해석한다.
- 관련 자료를 수집하거나 입력 자료를 읽는다.
- 중복을 제거하고 핵심 차이점을 정리한다.
- 최종 답변을 `핵심 요약 / 비교 / 다음 행동 / 출처` 형식으로 반환한다.

초기 출력 품질 목표는 다음과 같다.

- 답변 구조가 항상 일정하다.
- 출처가 있으면 함께 제시한다.
- 장황한 설명보다 실행 가능한 요약을 우선한다.
- 같은 질문을 다시 받아도 큰 틀의 품질이 흔들리지 않는다.

## 하지 않을 것
초기 단계에서는 아래 범위를 의도적으로 제외한다.

- 메일 발송, 일정 생성, 파일 수정 같은 외부 쓰기 자동화
- 에이전트끼리 무한히 상호 대화하는 복잡한 자율 루프
- 모든 주제를 다루는 범용 비서
- 30B 이상 대형 로컬 모델 전제 설계
- 완전 자동화된 장기 메모리 시스템

## 모델 및 운영 전략
`tmp.txt` 기준 판단을 현재 프로젝트에 맞게 정리하면 다음 전략이 가장 현실적이다.

- 로컬 모델은 주력 두뇌보다 저비용 보조 에이전트로 사용한다.
- 16GB 노트북 기준 기본 선택은 gemma3:4b이다 (한국어 안정성, 빠른 응답).
- 여유가 있으면 더 큰 모델을 실험하되, 기본 운영은 4B 안정성 우선으로 잡는다.
- 큰 코드베이스 이해나 긴 reasoning은 장기적으로 외부 강한 모델 fallback을 붙이는 방향을 검토한다.
- 오케스트레이터는 두꺼운 추론 엔진이 아니라 "누가 어떤 일을 할지 정하고 결과를 다시 모으는 얇은 제어층"으로 유지한다.

정리하면 초기 현실적 조합은 다음과 같다.

- Discord 인터페이스
- Python 오케스트레이터
- Ollama gemma3:4b 로컬 모델
- 필요 시 외부 provider fallback

## 목표 아키텍처
초기 목표 아키텍처는 아래와 같다.

```text
[Discord Bot]
    |
    v
[Supervisor / Orchestrator]
    |---- [Research Agent]
    |---- [Analyst Agent]
    |---- [Writer Agent]
    |
    |---- [LLM Provider Adapter]
    |         |---- Ollama
    |         └---- External Fallback
    |
    └---- [State / Logs / Source Records]
```

권장 새 구조 예시는 아래와 같다.

```text
assistant/
├─ app.py
├─ interfaces/
│  └─ discord_bot.py
├─ orchestrator/
│  └─ supervisor.py
├─ agents/
│  ├─ research_agent.py
│  ├─ analyst_agent.py
│  └─ writer_agent.py
├─ providers/
│  ├─ base.py
│  ├─ ollama_provider.py
│  └─ external_provider.py
├─ sources/
│  ├─ web_search.py
│  └─ document_reader.py
├─ storage/
│  └─ task_store.py
└─ prompts/
   └─ research_prompts.py
```

초기 구현 원칙은 다음과 같다.

- 처음부터 복잡한 agent-to-agent 대화 구조를 만들지 않는다.
- `Supervisor + 실행 에이전트 2~3개`의 2계층 구조로 시작한다.
- Writer는 초기에는 Supervisor에 합쳐도 된다.
- 중간 산출물은 자유 텍스트가 아니라 구조화된 형태로 남긴다.
- 읽기 역할과 쓰기 역할은 장기적으로 분리한다.

## 에이전트 역할 정의
### 1. Supervisor
- 사용자 요청 해석
- 작업 분해
- 어떤 에이전트를 호출할지 결정
- 최종 응답 조립

### 2. Research Agent
- 웹 검색 또는 문서 탐색
- 관련 자료 후보 수집
- 출처 정리

### 3. Analyst Agent
- 중복 제거
- 핵심 주장과 차이점 추출
- 신뢰도 판단

### 4. Writer Agent
- 사람이 읽기 쉬운 최종 응답 정리
- `핵심 요약 / 비교 / 다음 행동` 형식 유지

## 단계별 개발 로드맵
### Phase 0. 제품 명세 확정과 그린필드 스캐폴드 ✅ 완료
현재 저장소를 바로 확장하지 않고, 새 목표에 맞는 최소 구조를 먼저 세운다.

범위:
- 새 패키지 구조 확정
- Discord 입력 형식과 명령 표면 결정
- 리서치 응답 스키마 확정
- 현재 코드에서 가져올 부품과 버릴 부품 구분
- `Discord -> Supervisor -> Stub Response` 수직 슬라이스 생성

완료 기준:
- 새 구조에서 최소 실행 경로가 동작한다.
- 리서치 비서 MVP의 입력/출력 계약이 문서로 고정된다.
- 기존 코드 재사용 여부와 범위가 명확해진다.

### Phase 1. 단일 에이전트 리서치 응답 MVP ✅ 완료
멀티에이전트로 가기 전에 리서치 답변 형식을 먼저 고정한다.

범위:
- AI/개발 주제 전용 질문 범위 정의
- 고정 응답 형식 도입
- 질문 분류와 간단한 요약 템플릿 추가
- 자료가 있을 때 출처를 함께 정리하는 방식 확정

완료 기준:
- 한 번의 질문에 대해 `핵심 요약 / 비교 / 다음 행동 / 출처` 형식이 유지된다.
- 답변 품질이 일반 `!ask`보다 리서치 목적에 더 맞게 개선된다.

### Phase 2. 얇은 오케스트레이터 MVP ✅ 완료
실제 멀티에이전트처럼 보이는 최소 제어층을 추가한다.

범위:
- Supervisor 추가
- Research / Analyst 역할 프롬프트 분리
- 작업 ID와 중간 산출물 저장
- 결과 병합 규칙 정의
- 기본 타임아웃과 재시도 처리

완료 기준:
- 하나의 요청이 역할별 단계로 분리되어 처리된다.
- 중간 결과와 최종 결과를 로그에서 추적할 수 있다.
- 단순 단일 프롬프트보다 구조적으로 더 나은 결과가 나온다.

### Phase 3. 자료 수집 기능 확장 ✅ 완료
리서치 비서로서 실제 가치를 높이는 단계다.

범위:
- 웹 검색 연동 또는 제한된 외부 자료 수집 경로 추가
- PDF/문서 입력 처리 검토
- 중복 출처 제거와 출처 포맷 정리
- 주제별 검색 프롬프트 보강

완료 기준:
- 여러 출처를 모아 비교하는 흐름이 가능하다.
- 자료 목록과 최종 요약 사이 연결이 사용자에게 보인다.

### Phase 4. 운영 안정화 ✅ 완료
- ✅ 구조화된 로깅, 토큰/시간 측정, 에러 계층, 회귀 테스트
- ✅ Provider fallback → Phase 6에서 완료

### Phase 5. 기능 확장 ✅ 완료 (1차)
리서치 비서가 안정화된 뒤에만 외연을 넓힌다.

완료:
- ✅ 리서치 히스토리 저장 — SQLite, /history 커맨드 (조회/검색/페이징/상세보기)
- ✅ 후속 질문 — /followup 커맨드 (이전 리서치를 컨텍스트로 이어서 질문)

미래 후보:
- 요약 길이 조절 (/research --brief)
- PDF/URL 직접 입력 분석
- Notion/마크다운 내보내기
- 예약 리서치 (주기적 자동 조사)
- Calendar 읽기 재통합
- Mac mini 장기 운영 준비

완료 기준:
- ✅ 핵심 리서치 흐름을 해치지 않으면서 부가 기능을 추가할 수 있다.

## 성공 기준
다음 입력 예시를 안정적으로 처리할 수 있으면 1차 목표에 근접한 것이다.

> RAM 16GB 노트북에서 개인용 AI 비서를 구축하는 방법을 조사해서, 무료 / 저비용 / 확장형 3안으로 정리해줘.

성공 조건:

- 관련 자료를 모은다.
- 중복 없이 정리한다.
- 비교 가능한 2~3개 안으로 압축한다.
- 추천안과 이유를 제시한다.
- 다음 행동과 출처를 함께 준다.

## 예상 작업량
`tmp.txt` 기준으로 보면 개발량은 아래 정도가 현실적이다.

- 얇은 프로토타입: 1~3일
- 개인이 실제로 쓰기 시작할 수 있는 수준: 1~3주
- 안정적인 멀티에이전트 운영형: 그 이상

시간이 오래 걸리는 부분은 모델 연결 자체보다 아래 항목이다.

- 실패 재시도
- 타임아웃 처리
- 상태 관리
- 중간 결과 전달
- 품질 검증
- 역할 충돌 방지

## 주요 리스크
- 로컬 모델 품질 한계로 리서치 품질이 불안정할 수 있다.
- 자료 수집 기능이 붙는 순간 출처 신뢰도 관리가 중요해진다.
- 멀티에이전트 구조를 너무 빨리 복잡하게 만들면 구현량만 커지고 품질이 오히려 흔들릴 수 있다.
- 캘린더, 메일, 파일 수정 같은 쓰기 기능을 일찍 붙이면 안정화 부담이 급격히 커진다.
